# 候选创新方向

以下方向都遵守同一约束：**必须回答"解决了校园场景中的什么真实问题"，并且"能用指标证明比传统方案更好"**，禁止伪创新（再加一个 Agent/向量库/MCP/重排器/模型）。

---

## 方向 1：校园知识时效性引擎（Temporal Grounding）

- **用户问题**：校园通知/制度有强时效性，学生常拿到过时信息（如旧版奖学金条件、已过期的通知）。
- **技术假设**：给每条知识块加时间元数据（publish_date / effective_date / expire_date），检索时做时效过滤与加权，回答中标注"该信息发布于 X，有效期至 Y"。
- **为什么当前方案解决不好**：chunk 只有 `title/category`，无时间维度；检索无时效过滤；回答不标注时效。
- **方案**：chunk metadata 扩展时间字段；检索 query 时按时间过滤/降权过期块；生成时输出时效标注。
- **与现有开源项目区别**：FastGPT/Dify 的 RAG 无"校园时效"语义；本项目把时效作为一等公民。
- **实现复杂度**：低。
- **可验证指标**：过期信息召回率下降；时效标注准确率。
- **风险**：需人工维护知识的时间元数据。
- **是否推荐**：✅ 强推（直接命中项目立意"信息存在≠可用"）。

## 方向 2：信息源可信度分层（Source Credibility）

- **用户问题**：校园信息散落在官网通知、学院文件、公众号、论坛，可信度差异大，学生难以判断该信谁。
- **技术假设**：为每个 source 打可信度分，检索融合时加权，回答标注来源可信度。
- **为什么当前方案解决不好**：所有 chunk 平权，无来源可信度概念。
- **方案**：source 注册表 + 可信度分；检索时加权；引用时展示来源级别。
- **与现有开源项目区别**：通用 RAG 项目做"引用来源"，但不做"来源可信度分层"。
- **实现复杂度**：中。
- **可验证指标**：引用错误率下降；用户对来源的信任可解释。
- **风险**：可信度评分规则需人工定义，可能主观。
- **是否推荐**：✅ 推荐（与时效性同属"可信 grounding"主题）。

## 方向 3：Agentic RAG 自校正闭环

- **用户问题**：检索不准时答案质量差、甚至编造。
- **技术假设**：检索后加"相关性分级 → 不相关则改写重试 → 生成时强制 grounding"的闭环，可显著降低幻觉。
- **为什么当前方案解决不好**：当前是 naive RAG，无失败检测、无改写、无 grounding。
- **方案**：在 LangGraph 图中加 grade → rewrite → retry 回边 + grounding prompt。
- **与现有开源项目区别**：与 LangGraph-Chatchat 的 base_rag 同思路，但落地到校园知识场景。
- **实现复杂度**：中。
- **可验证指标**：幻觉率下降、无依据回答率下降、答案准确率提升（用评测集测）。
- **风险**：多一次 LLM 调用增加时延与成本；需设重试上限防死循环。
- **是否推荐**：✅ 强推（这是 RAG 从"能跑"到"可靠"的关键）。

## 方向 4：评测优先工程（Evaluation-first）

- **用户问题**：无法证明"比传统方案/naive RAG 好"。
- **技术假设**：建立校园问答评测集 + 指标（检索命中、答案准确、引用正确、意图准确、时延），用数据说话。
- **为什么当前方案解决不好**：只有冒烟测试，无质量指标。
- **方案**：建 dataset + runner，做 A/B（naive vs hybrid vs agentic RAG）对比，输出指标报告。
- **与现有开源项目区别**：Campus-Asistant 有基础 eval，但本项目可做成"评测报告即创新点"（用指标证明改进）。
- **实现复杂度**：中。
- **可验证指标**：本身就是指标产出。
- **风险**：评测集质量依赖人工标注。
- **是否推荐**：✅ 强推（最大差异化，答辩最有说服力）。

## 方向 5：事务闭环（意图→参数→澄清→执行→验证）

- **用户问题**："查课表/成绩"这类事务缺参数（学号/班级）时，系统应澄清而非乱答；执行后应验证结果。
- **技术假设**：把查询类工具建模为"参数抽取 → 缺失澄清 → 执行 → 结果验证"的状态机。
- **为什么当前方案解决不好**：tool 缺参数直接返回 mock，无澄清、无验证。
- **方案**：Tool 返回结构化结果（含 missing_params/error），Agent 触发澄清；执行后校验。
- **与现有开源项目区别**：Campus-Asistant 有 clarification_needed，本项目可进一步加"执行后验证"。
- **实现复杂度**：中。
- **可验证指标**：任务完成率、澄清次数、错误执行率。
- **风险**：需要真实教务接口（当前是 mock，需以 mock 模拟澄清/验证流程）。
- **是否推荐**：✅ 推荐（服务"事务执行"立意）。

## 方向 6：长期记忆落地

- **用户问题**：不记得"我是谁、问过什么"，每次重新解释。
- **技术假设**：落地 user_profile（专业/年级/偏好）+ 跨会话记忆 + 对话摘要。
- **为什么当前方案解决不好**：表已建未用，只有近 10 条消息。
- **方案**：用户画像写入、历史摘要、跨会话上下文注入。
- **与现有开源项目区别**：通用项目有 session memory，但校园画像（专业/年级）是场景特化。
- **实现复杂度**：中。
- **可验证指标**：多轮上下文相关度、重复询问率。
- **风险**：隐私（需脱敏、不存敏感信息）。
- **是否推荐**：可选（文档已写"记忆机制"，落地可自洽）。

## 方向 7：不确定性与置信度表达

- **用户问题**：低置信度时系统仍给出确定语气，误导学生。
- **技术假设**：基于检索得分/相关性分级输出置信度，低置信度时明说"我不确定/建议人工确认"。
- **为什么当前方案解决不好**：无置信度概念。
- **方案**：把 grade/score 转为置信度，生成时按置信度调整措辞。
- **与现有开源项目区别**：多数项目不显式表达置信度。
- **实现复杂度**：低。
- **可验证指标**：低置信场景幻觉率、用户信任度。
- **风险**：置信度阈值需调优。
- **是否推荐**：可选。

---

## 优先级排序建议

1. **方向 4（评测）** + **方向 3（agentic RAG）** — 组合拳：先用评测集证明现状有幻觉，再用 agentic RAG 修复并用同一评测集证明改进。
2. **方向 1（时效性）** + **方向 2（可信度）** — 校园特有、成本低、直接服务立意。
3. **方向 5（事务闭环）**、**方向 6（记忆）**、**方向 7（置信度）** — 按剩余时间取舍。
